## FAQ：`runs.jsonl` 是什么？

`runs.jsonl` 是 **append-only 运行日志**：位于 `.prismnext/experiments/<experiment-id>/runs.jsonl`，**每一行一个 JSON 对象**（`ExperimentRunEntry`），记录一次命令执行的结构化快照。

| 字段 | 含义 |
|------|------|
| `runId` | 唯一 run id（`run-YYYYMMDD-HHMMSS-xxxx`） |
| `startedAt` / `finishedAt` | ISO 时间戳 |
| `command` | 在实验岛 cwd 执行的 shell 命令 |
| `cwd` | 项目相对路径（如 `experiment/exp-20260707-lr-a3f2/`） |
| `exitCode` | 进程退出码 |
| `stdoutTail` / `stderrTail` | 输出尾部（各最多 4KB，ANSI 已剥离） |
| `artifacts` | 可选：相对 workspace 岛的路径列表 |
| `env` | `detect_env` 快照（python/R/git/venv 等） |
| `notes` | 可选注释 |

> **字段补充说明（源码核查）：** `stderrTail` 在当前 executor 中**永远是空字符串**——node-pty 把 stderr 合并进 stdout（`experiment-run-executor.ts` 硬编码 `stderrTail: ""`）。schema 字段保留以兼容，但 **UI runs 表只展示单个 "output" 列**，不拆 stdout/stderr 两列（否则一列常空，误导）。

**与 workspace 文件夹的关系：**

```text
.prismnext/experiments/exp-xxx/     ← registry（Platform）
  meta.json                          — 标题、briefLinks、workspacePath 指针
  runs.jsonl                         ← 本 FAQ 的文件（仅 append）

<experiment-dir>/exp-xxx/            ← lab（Agent / 用户自由布局）
  (scripts, results, .venv, …)       — 不在 registry 内硬编码子目录
```

**为何不应手动编辑 `runs.jsonl`：**

1. Agent module 纪律要求 run 与 `env` / `exitCode` 一致；手改会破坏 `methodology-auditor` 的事实依据。
2. 无 schema 校验 UI；一行 malformed JSON 会导致 `read` 跳过该行（当前**静默跳过**，P1 加 parse 警告）。
3. 唯一合法写入路径：`appendRun()`（service）← `experiment-log append_run` 或 `experiment-run` executor。

**允许的人类操作：** 只读打开、复制 run 内容、在 Files mode 中查看 artifact 文件。**P2 可选：** 「Export runs as CSV」只读导出，仍不鼓励手改 jsonl。

## 设计决策（源码核查 — 2026-07-08 新增）

经 4 路并行源码核查得出，记录"为什么"：

### D1. mode 模板 = list-in-Content，**不**用 literature reader 壳

literature-mode 有个 PDF reader keep-alive 壳，被 **4 处硬编码特判**：

- `src/renderer/components/layout/right-main-area.tsx`（`LiteratureReaderShell` / `literatureShells` 栈 + `withLiteratureKeepAlive`）
- `src/renderer/components/layout/right-area.tsx:810`（`hideBreadcrumb` 硬编码 `focusedMode === "literature"`）
- `src/renderer/stores/right-panel-store.ts:562`（`ensureTab("literature")` 关 tab 复活）
- `src/renderer/lib/workspace/tab-lifecycle.ts`（`getLiteratureTabCloseAction` literature-only）

literature 的 Content 在 detail 时 `return null`——reader 由 `RightMainArea` 渲染，为保活 PDF 滚动/笔记状态。

experiments 的 runs 表**不需要保活**（无 PDF 滚动状态可丢）。照搬 literature 会无谓拖入 4 处特判。**决定：** 结构对标 literature 的 **list 部分**（`LiteratureLibrary`——列表+详情都在 Content 内）或 git-mode/files-mode；**不**改 `right-main-area.tsx`；**不**实现 reader 壳。若后续 run-detail 真有保活需求，再单开。

### D2. executor refactor 经核实是"小幅"

`kickoffExperimentRun`（`src/main/services/experiment-run-executor.ts`）与 bridge 的唯一耦合是 `resPath` 参数 + `writeResult`（10 行 `writeFileSync`）。`resPath` 仅在 4 处出现（args / destructure / 4 个 `writeResult` 调用点）。PTY（`runAiCommand`）、10min timeout（`runWithTimeout`）、`detectEnv`、`appendRun` 全部 bridge 无关。refactor ≈ 25 行单文件（`resPath` optional + `onComplete` callback），bridge 调用方零改动。**决定：** plan 原"小幅 refactor"判断准确，照做。注意早返回错误分支（`experiment_not_found` / `missing_command`）会**同步**触发 callback——IPC handler 需容忍同步回调（或 `process.nextTick` defer）。

### D3. UI Run confirm = mode 内 modal，**不**复用 `registerBashJobIntent`

源码核实：shell-confirm 基础设施**结构性地绑死在 ACP tool-call 生命周期**，三处耦合：

1. **触发**：`session/permission` 事件只在 `acp/service.ts:366` 的 `requestPermission` 里发——纯 UI 无等价入口。
2. **身份**：confirm state keyed by `{ tabId, toolCallId, permissionId }`，全是 ACP/chat-tab 概念，UI Run 无这些。
3. **执行**：`executeApprovedBashJob` / `runApprovedBash` 只能从 `answerPermission`（ACP answer 路径）调。

`registerBashJobIntent`（`ai-bash-runner.ts:79`）是给自定义 `bash` tool 的**文件桥标记**（写 `.active-tool.json` 让 bash tool 轮询），**不是 UX 入口**——plan 原"方案 A 推荐 P0"是死路，复用它只会写没人轮询的文件。

**决定：** 走 mode 内 modal（原方案 B），但用 **`resolvePermissionAction(mode,"experiment-run")`**（`permission-modes.ts:122`，**纯函数**）咨询规则保持等价：

- `readonly` → 禁用 Run 按钮
- `ask` / `auto` → 弹 modal 展示 command + cwd + Allow/Deny

可复用 `shouldShowPermissionGate`（`permission-gate-panel.tsx:48`，纯函数）做 gate 谓词。P0 **只 per-run**，"Always allow in project"留 P1（本质是改 permission mode，settings 级动作，不该藏 modal）。为与 Agent 路径一致，UI modal 复刻 120s UI timeout（`PERMISSION_UI_TIMEOUT_MS`）。

### D4. experiments 是首个**纯净**双轨

brief 的人类 UI（`research-brief-panel.tsx`）实际用通用 `fsRead`/`fsWrite` 编辑整文件 markdown，**没**走 `researchBrief:*` domain IPC（该 IPC 主要给 Agent/程序化访问）。所以 brief 不是纯净双轨样本。experiments 反而是首个 UI 真调 domain IPC 的纯净双轨（list/read 是结构化，非整文件编辑）。**含义：** UI 接线层不能直接抄 brief panel，得自己接 IPC。

### D5. 抽 `resolveExperimentCtx(projectRoot)` 共享 helper

experiment IPC 比 brief 多一步解析：`resolveExperimentDir`（`workspace-config.ts:218`）+ `buildExperimentStorageContext` + `no_experiment_folder` 错误映射，现内联在 `experiment-log-bridge.ts:91-100`。IPC 照抄就重复。**决定：** 抽 `resolveExperimentCtx(projectRoot): ExperimentStorageContext | { ok:false, error, hint }` 给 bridge + IPC 共用。

### D6. P0 砍 `create`/`updateMeta` 的理由

新项目默认无 experiment 文件夹（`workspaceDirs` 默认只 `manuscript`，experiment 是 opt-in）。第一道摩擦是"加文件夹"不是"建实验"。加完文件夹后 Agent 建第一个实验**更准**（读 brief 填 `briefLinks`）。人类 New 表单 + brief picker 是 P1 锦上添花，非 P0 阻塞。P0 面越小越快验证双轨跑通。**故 P0 IPC 不含 `create`/`updateMeta`。**

## 设计原则

### 1. 单源真相（Single source of truth）

所有 list / read / create / run **必须**调用 `experiment-log-service` + `kickoffExperimentRun`。**禁止** renderer 直接 `fsRead`/`fsWrite` registry 文件（与 Agent module 纪律一致）。

### 2. Settings ≠ 工作区

| 归属 | 内容 |
|------|------|
| **Settings → Workspace** | 配置 `function: "experiment"` 的顶层目录名 |
| **Settings → Prompts & Rules** | Research brief 编辑（保持） |
| **Right Area → Experiments mode** | 实验列表、详情、runs、UI run、brief 摘录、打开 lab 文件夹 |

### 3. Agent 与人类 UI 分工

| 操作 | Agent（Chat） | 人类（Experiments mode） |
|------|---------------|---------------------------|
| 创建实验 | `experiment-log create` + briefLinks | **P1** — 「New experiment」表单（同 service） |
| 写脚本 / 改代码 | `edit` / `write` | Files / TeX workspace 打开 `workspacePath` |
| 执行并记 log | **`experiment-run`（优先）** | **Run 面板** → IPC → **同一 executor** |
| 浏览 runs | `experiment-log read` | Runs 时间线（只读，单 output 列——见 FAQ） |
| 改 meta / tags | 无专用 tool（P1 `update_meta`） | **P1** — 编辑 title / tags |
| 手改 runs.jsonl | ❌ module 禁止 | ❌ UI 不提供编辑器 |
| 方法审计 | Task methodology-auditor | 可选「Send snapshot to Chat」按钮（P1） |

### 4. UI 触发 run — 为何值得做

仅依赖 Chat Agent 的问题：

- 用户已写好脚本，只想 **重跑上一条 command**，不必组织自然语言。
- 需要 **对照 runs 表 + 输出 tail**，Chat widget 信息密度不够。
- UI run 若走 **同一 executor**，不破坏 Sprint 0.3 的 log 纪律。

## Remote 服务器：Terminal 够吗？

### 现有 Terminal 能力

- `terminal:create` → 本地 **node-pty** + 用户默认 shell（bash/zsh）；`cwd` 可设为项目内任意绝对路径（含 experiment 岛）。
- 用户可 **手动** `ssh user@host` 进入远程交互 shell。

### Terminal **能**做的

- 交互式远程调试、vim、htop、手动 pip install。
- 作为 **「未纳入 experiment log 的探索性 shell」**（module 已允许裸 bash，但需 Agent 自己 append_run）。

### Terminal **不能**自动提供的（Experiments 产品缺口）

| 能力 | 为何 Terminal 不够 |
|------|---------------------|
| 写入 `runs.jsonl` | 裸 ssh 会话不在 `experiment-run-executor` 流水线内 |
| `detect_env` 快照 | executor 探测的是 **本地** island 路径上的 python/R/git |
| 与 experiment id 绑定 | Terminal tab 无 `experimentId` 元数据 |
| 远程 cwd = 远程 lab 路径 | 本地 PTY 的 cwd 是本地路径；ssh 后 cwd 在远端，Prism 不跟踪 |
| 权限 / 审计 | `experiment-run` 走 `shell` permission group；随意 ssh 无统一 confirm UX |

> **Terminal cwd 无沙箱（源码核查）：** `terminal:create` 把 `cwd` 直传 `pty.spawn`，v0.5.4 的 fs path sandbox **只管 `fs:*` IPC**，不管 terminal。"Open terminal in lab" 可行（IPC 已支持任意 cwd），但需知晓此安全面。

### 结论与分期

| 阶段 | Remote 策略 |
|------|-------------|
| **Sprint 0.7（本计划）** | 文档化：**交互远程 = Terminal**；Experiments mode 提供 **「Open terminal in lab folder」**（本地 cwd = islandAbs）。**不做** SSH 配置 UI。 |
| **Sprint 0.8+（Future）** | Platform：`remoteTargets[]` + `experiment-run` 的 `target: "remote:<id>"` + 远程 executor；mode 内显示连接状态。**单独 spec：** `sprint-0.8-remote-experiment-run.md` |

## IPC 契约（新建 `experiment:*`）

**模式：** 与 `researchBrief:*` 相同 — main handler 直接调 service，**不**经 OpenCode bridge。薄包装，零验证（service 拥有验证），错误返回 `{ ok:false, error, hint? }` 不抛。

### P0 channels

| Channel | 参数 | 返回 | 说明 |
|---------|------|------|------|

### `experiment:run` 异步语义

Agent tool 用 bridge 轮询 `.result.json`；UI 用 **IPC + main 事件**：

1. Renderer 调用 `experiment:run` → main 经 `resolveExperimentCtx` 校验 + **shell 确认**（见 D3，mode 内 modal 已在 renderer 侧完成，main 侧仍用 `resolvePermissionAction` 复核 mode）→ 立即返回 `{ ok: true, runId, status: "started" }`。
2. Main `kickoffExperimentRun({ …, resPath: null, onComplete: broadcast })`（refactor 见 D2）。
3. Main 向 renderer 发送 `experiment:runComplete`（含 `run` JSON）。
4. Store 更新 runs 列表；detail 自动 append 新 run 行。

**禁止** UI 调 `terminal:runAiBash` 绕过 log。

## UI Run 与权限（Shell confirm）

`experiment-run` tool 注册为 `permissionGroup: "shell"`, `confirmUx: "command"`（`tool-permission-registry.ts:92`）。

> **注意（源码核查）：** `tool-permission-registry` 只管 **Agent tool**——UI 走 IPC 不经过它。`confirmUx: "command"` 只在 renderer `PermissionGatePanel` 渲染标签时被消费，无 main 作用。故 UI Run 的 confirm 是**独立**于 tool registry 的 renderer 侧 UX（见 D3）。

UI Run 按钮 **必须**等价确认（见 D3）：

- `readonly` mode → 禁用 Run 按钮
- `ask` / `auto` mode → 弹 **mode 内 modal**：展示 command + cwd + Allow/Deny，120s timeout 自动 deny（对齐 Agent `PERMISSION_UI_TIMEOUT_MS`）
- gate 谓词复用 `shouldShowPermissionGate`（纯函数）

Run 进行中：按钮 disabled + spinner；允许 **Cancel** → 调 `experiment:cancelRun` → `cancelAiCommandForSession("experiment:<id>:<runId>")`（sessionId 方案 executor 已用，见 D2/D3）。

**P0 只 per-run**；"Always allow in project" 留 P1（本质改 permission mode）。
